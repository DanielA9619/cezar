# Milestone 1C.1 — owner enrollment and GitHub verification

The queue remains mock-only. A linked GitHub issue needs a local roadmap task, a fresh completed queue refresh, and a direct GitHub read during grant preparation, after the owner signs, before dispatch, and before each RunManager continuation or spawn. The direct reader uses `gh api` for the repository and one issue, with bounded execution and output; a missing `gh` login, inaccessible/deleted issue, malformed response, or rate limit fails closed. It does not paginate because it reads a numbered issue directly. The existing queue refresh paginates its list separately.

The approved snapshot records GitHub repository and issue numeric and node IDs, issue number, `updated_at`, and SHA-256 of the returned state, state reason, title, body, and label IDs/names. Repository remote and allowlist must match. A changed issue, lost `roadmap-approved` label, closure, changed local task or workflow, or evidence older than 30 seconds blocks the next execution. Issue text is task data only; it never grants authority. The owner signs the snapshot as part of the exact WebAuthn grant. The cockpit shows the task, canonical repository root, runner, workflow, scope, verifier, expiry, attempt limit, review rule, and issue snapshot before the owner starts a fresh Windows Hello challenge. Revocation also requires a fresh signed assertion. Existing approved grants can run unattended until expiry or revocation, with direct issue checks at execution boundaries.

**Revision limit:** GitHub `updated_at` is metadata, not an immutable revision token. The digest also catches observable edits within one timestamp tick, but a change followed by a restoration between reads may escape detection. GitHub has no atomic compare-and-launch operation here. A change can occur after the last read and before an agent operation begins, and an already-running operation cannot be preempted synchronously. The five-second heartbeat checks local revocation and expiry; direct GitHub reads occur at launch and continuation boundaries. This is a best-effort snapshot comparison, not perfect revision locking.
