# Milestone 1C — authorized mock execution bridge

Branch: `codex/milestone-1c-execution-bridge`, based on `e976386f`.

## Owner authorization and boundary

The owner selected Windows Hello. Cezar enrolls a local WebAuthn platform credential in the cockpit and verifies signed assertions with `@simplewebauthn/server`. Every grant or revocation uses a new, two-minute challenge. The grant challenge includes a digest of repository name and canonical root, task identity and revision, scope, runner, workflow and revision, expiration, attempt cap, fixed verifier, and review requirement. Verification checks the signature, origin, RP ID, challenge, counter, and user-verification flag. A PIN dialog alone never authorizes work. There is no passphrase fallback. An approved grant can be used later without another Hello prompt until it expires, changes, or is revoked.

The trust boundary is the Windows account, the installed Cezar code, and the local cockpit. Repository, issue, workflow, and agent text is untrusted task data. A process already running with full privileges as the same Windows user can modify Cezar's local state or invoke the platform authenticator and is outside this milestone's claim. WebAuthn registration requests a platform authenticator and checks the reported attachment, but attestation is `none`; the server cannot cryptographically prove the credential was made by Windows Hello rather than another platform authenticator. A real Windows Hello enrollment and browser compatibility check remain necessary on the owner's device. See [Microsoft's Windows Hello WebAuthn API guidance](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/webauthn-apis) and the [WebAuthn verification rules](https://www.w3.org/TR/webauthn-1/).

Older CLI approval records cannot run. The CLI no longer grants or revokes; it directs the owner to the cockpit. The server keeps the authorization history and credential counter in its atomic, locked queue state. An absent Hello credential or failed challenge stops approval and execution.

## Execution boundary

`cezar roadmap queue dispatch [task-id]` is the only dispatch entry. It rechecks the candidate, atomically persists a claim with an owner, UUID, generation, heartbeat, and state, then starts the existing `RunManager`. Queue runs carry claim provenance in their run record. RunManager checks the authorization and claim before launch, continuation, agent steps, and verification. It selects hardcoded bundled mock Claude/Codex runners for queue records, gives them a reduced environment, limits verification to the bundled fixed command, and disables auto landing. The mock workflow deliberately writes a defect, fails verification, corrects it on the second attempt, verifies successfully, and reaches review. Review must be enabled in the disposable project's config. No queue path calls a real provider.

Execution is restricted to Windows, an explicitly set isolated `CEZ_HOME`, and a marked disposable Git repository beneath `CEZ_HOME/roadmap/disposable`. The queue allowlist must name its registered project. The only approved scope is `.` within that disposable repository, the only verifier is `cezar:mock-verify`, and attempts are capped at three. Repo scripts and hooks can still run through the existing worktree lifecycle, so the disposable repository must contain only controlled fixture content. Milestone 1C.1 adds direct GitHub verification for linked local roadmap tasks; see [the follow-up record](milestone-1c1.md). Discovered issues without a linked local task remain denied.

Claims are never stolen automatically after a missed heartbeat. The same claim remains in `review`, `failed`, or `uncertain` after termination, preventing restart or a second scheduler from launching duplicate work. An uncertain process cleanup retains the claim. Revocation or expiry stops future launches and is checked before subsequent steps; a running mock is cancelled by the heartbeat check within five seconds. This cannot preempt an operation already in progress immediately.

## Validation and remaining work

- The focused integration tests create disposable Git repositories and isolated `CEZ_HOME` directories, prove an unapproved second task stays ineligible, run both bundled Claude and Codex mocks through correction and verification into review, refuse a second dispatch after restart, admit only one of two competing dispatchers, and fail at verification when the attempt limit is one. Queue claim tests cover competing claimants and retained uncertain claims.
- A software WebAuthn test credential signs a fresh challenge. The server accepts the valid user-verified signature and rejects a forged signature and a stale challenge. This checks the cryptographic path without claiming a real Windows Hello interaction happened in CI.
- Focused bridge, queue, contract parity, and typed-body tests pass (13 tests). TypeScript typecheck, unit tests, production build, and package tests pass. The broad Windows Vitest suite was started but interrupted after widespread workflow failures; an isolated rerun showed those failures originate in Windows `rmSync` cleanup returning `EPERM` for temporary repositories. This result is not a passing broad suite.

**Recommendation: NO-GO for a supervised real-agent queue task.** Complete and test live GitHub issue revision verification, confirm real Windows Hello enrollment and approval in the desktop browser, and settle the broad suite before any real-provider bridge is proposed. Milestone 1C stays mock-only. No automatic acceptance, merge, deployment, remote exposure, credential change, or usage-budget automation was added.
